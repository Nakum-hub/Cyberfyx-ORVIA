# A06: real regression, recovery and backend network checks

The existing `start_test` and `test_run` contract operations now persist runs in PostgreSQL. A verified staff SUPER_ADMIN can enqueue an allowlisted scenario for the exact enrolled synthetic installation/scope/profile. Current authority, named profile, build and contract are checked again by the protected local operator at execution. Stable committed acceptance replay remains unchanged. A profile lock prevents concurrent runners; a scope lock and unique active-run constraint prevent overlap. Each assertion is persisted separately; terminal run documents are immutable and audited. Evidence exports link the actual persisted run.

`regression:init confirm:<profile>` enrolls only the protected Aster fixture journal. `regression:run confirm:<profile>` consumes one pending run using operator-held local credentials; it is not a web endpoint or an application-role subprocess launcher. It requires exclusive use of its fixture profile. The API records NOT_RUN until the operator executes it. The operator creates fresh scoped configuration through actual authenticated HTTP, then uses PostgreSQL, OPA, Temporal, signed agent effects, current send admission and independent target reads. No result selector or in-memory workflow is used.

The broken scenario runs an intentionally stale-preview sender in `tests/fault-fixtures/stale-sender.ts`. It writes a real isolated synthetic output row after withdrawal; the ordinary assertion observes the output count and records FAIL. `expected_fault_detection` explains the negative fixture and never converts that FAIL to PASS. Healthy, broken, repaired and restoration runs retain separate IDs. Interrupted runners become ERROR with durable assertion records; there is no fictional success/resume. A process interrupted after creating child services may require stopping those owned services before another exclusive run; the operator refuses an already-active worker/agent.

Target restoration operates only on a persisted run-owned snapshot and the named synthetic target. It retains the authoritative current consent ledger, increments target generation, restores the old target fields into quarantine, and commits the target first. If the control update fails, quarantine/generation mismatch prevents processing; cross-database atomicity is not claimed. Old-generation commands fail. A current-generation signed restriction and independent scoped read precede guarded activation. The recovery journal artifact contains the actual snapshot, signed recovery envelope, receipt and observed state; no private key is exported. This is target-only recovery, not recovery of the entire control plane.

`test:isolation` proves wrong profiles/confirmations, unenrolled resources and arbitrary simulator modes are rejected without changing the observed database state. The auth regression exposed missing forced RLS on the operator-only fault-output table; append-only migration 0014 corrects it without granting an application policy. The original failed invariant and corrected suite are retained. The existing reset command still refuses a business schema and active Temporal jobs. No business reset, other-lane reset, volume deletion or customer target is introduced.

`runtime:build` captures enumerated Git candidate source into a separate build context, verifies hashes and installs the pinned lockfile. Ignored credentials, runtime stores and caches never enter the context. `test:network confirm:codex-a00` uses a container attached only to the internal owned service network, fixed private service relays, deny-all local DNS and a controlled canary on another temporary network. It verifies the canary in a positive control, attempts denied DNS/IP access, executes the real core, and checks the canary count and actual local service connections. Cleanup verifies nonce ownership before removal. This qualifies the tested backend container boundary only; host development and browser egress need their own evidence.

Dependency matching downloads GitHub's public reviewed npm advisory feed and matches every package section of the pinned lockfile locally; no dependency list is uploaded. The original esbuild 0.18.20 finding is retained. The selective `@esbuild-kit/core-utils>esbuild` override pins 0.28.2, already used by the current toolchain, with actual synchronous/asynchronous transform, build, auth and workflow verification. Deprecated core-utils/esm-loader still originate in Drizzle Kit; no claim of universally vulnerability-free dependencies is made. Feed snapshot hashes, original finding and corrected results are artifacts. `dependencies:check --refresh` downloads the public feed; `dependencies:check` reuses the protected local cache.

Contract transport stays 0.4.0 and signed commands stay 0.3.0. Generated implementation metadata changes for the two existing test endpoints only. Migrations 0013 and 0014 are append-only and require the existing roles/bootstrap order. Work retains semantic/security acceptance; UI/browser tests and final rehearsal are separate gates. Exact commands, results, failures, source identities and artifact checksums are in the A06 publication index and handoff.

Serial suites share the real loopback MFA bucket. A back-to-back evidence setup received 429, confirmed in the auth audit, and was rerun after the real window elapsed. Authentication limits were not disabled or weakened. The Docker engine had also been stopped at resume; the connection failure and named-service restart are retained. Docker emits a variable-name heuristic warning for BETTER_AUTH_TELEMETRY=0; that value disables telemetry and is not a credential.

The multi-scenario integration coordinator waits for the real authentication audit idle window between independent scenarios. It neither deletes rate-limit state nor changes the runtime authentication policy. This prevents fast consecutive synthetic scenarios from accumulating MFA attempts in a single sliding idle window. Earlier setup ERROR records remain intact.
