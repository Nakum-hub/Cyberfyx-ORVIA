### R1 remains HIGH — previously signed responses bypass the new review

`backend/domain/src/dpdpa-audit/channel.ts:328` and `:341`; `database/customer/migrations/0070_finding_response_personal_data_review.sql:6`.

An installation upgrading with a signed UNKNOWN response from 0.45 has NULL personal_data_review. The guard checks that field only when `!r.signed`. The saved signed body is retried over the network without the new confirmation. A newer vendor rejects the old approval schema, but the personal data has already left the installation. Migration 0070 neither classifies nor quarantines those pending signed rows. Ordinary new approvals correctly require a distinct privileged approver and record the review.

Proposed fix: require the review for every send, including retries, and validate the saved signed approval. Quarantine legacy signed pending rows without altering their immutable signatures; retain UNKNOWN effect where appropriate and require a newly reviewed response. Add an upgrade regression with a previously signed UNKNOWN row and assert zero outbound requests containing it.

### R2 remains HIGH — the answer budget excludes request selection

`backend/vendor/audit/channel.ts:117`, `:124`, `:136`; `database/vendor/migrations/0006_audit_channel.sql` function `channel_pending_requests`.

The document loop respects a byte budget, but all 200 pending requests are included first and returned even if that base answer exceeds the limit. A valid 2,000-character Devanagari description in each request produces a signed answer of **1,304,094 bytes**, without any documents. The client rejects it above 1,048,576 bytes and cannot acknowledge those requests, so later check-ins repeat the same failure. The checked-in reproduction uses real contracts and signatures, no database or network.

Proposed fix: select requests and documents under one actual UTF-8 signed-answer budget; retain unsent requests durably and prevent awaiting-approval requests from permanently starving later work. Test a maximum multibyte request batch and a mixed request/PDF batch. The PDF batching and explicit TOO_LARGE_FOR_CHANNEL state themselves address the original PDF-only case.

### R7 remains MEDIUM — inactive mandates still call the vendor

`backend/domain/src/dpdpa-audit/channel.ts:363–365` (primary location line 365).

Local queue settlement now occurs before the call, so vendor downtime no longer prevents settlement. However, suspension, revocation or expiry still enters checkIn. Revision 1.6 forbids calls without an active mandate; no owner exception is recorded. This also uses the ordinary check-in body with acknowledgements, not a distinct terminal-state-only protocol.

Proposed fix under the current baseline: return after local settlement while inactive. Any terminal-notification exception requires an explicit owner baseline decision first, followed by a narrowly specified payload and regression coverage. Do not describe R7 as fully fixed.
