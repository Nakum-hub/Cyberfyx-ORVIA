## Prioritized findings

1. **Pending canary retirement is inconsistent between API and database; minimal fix implemented, execution NOT_RUN.** `backend/domain/src/consent/canaries.ts:retireCanary` allows PENDING retirement and `database/customer/migrations/0079_withdrawal_canaries.sql:canary_guard` allows PENDING -> RETIRED. The table CHECK equates PENDING with NULL `activated_at`, so that retirement fails. Root allocated new migration 0086: it requires PENDING to have no activation and ACTIVE to have activation, permitting retirement with or without prior activation. It preserves the activation actor/time pairing, two-person restriction and every history/RLS guard; it does not edit an applied migration. New HTTP suite covers pending retirement, exact idempotent replay, repeat retirement refusal, retired activation refusal, role/foreign-tenant denials, self-activation refusal and active retirement retaining activation history. Root must run the unchanged suite before 0086 (expected regression failure) and after 0086 (ordinary healthy control).

2. **Canary grant-then-send adverse case is missing.** `backend/privacy-control/src/processing.ts:admitSend` calculates and persists the ordinary admission result and possible send record before calling the void canary trap. The trap records an attempt without changing admission. Migration 0079 describes SEND_ADMISSION as BLOCK; implementation says the attempt is recorded whatever the decision. Existing `tests/integration/consent/canaries.test.ts` proves BLOCK only for a never-consented principal, then records a grant without testing admission again. Add a fixture that establishes every ordinary ALLOW prerequisite after a fraudulent grant, and requests marketing admission. Product/contract question: observational decoy versus unconditional active-canary block. Do not silently introduce a new admission authority until that conflict is resolved.

3. **Real-person canary designation needs a decision.** `createCanary` checks scoped principal existence, not `synthetic`. After real admission, a real principal could be designated as a canary. Outbound delivery deliberately accepts messages to a canary and assumes an organisation-owned decoy mailbox. The revision 1.9 real-principal addendum does not settle whether real withdrawn people can be decoys. Proposed decision: require a synthetic organisation-controlled decoy, or expressly define allowed real-canary treatment and transport restrictions. Regression belongs in the isolated before/after-admission scratch fixture, using synthetic data only.

4. **Production criteria approval cannot see retained verification items through PracticeState.** `backend/vendor/audit/practice.ts:recordProductionCriteria` stores source hashes and `open_verification_items` in `criteria_versions.sources`. Its comment promises the approver sees them; `practiceState` and `shared/contracts/src/vendor-practice.ts:PracticeState` omit those details, and the browser suite only approves the version row. Proposed coordinated canonical-contract change: an approved criteria detail/review surface with the retained package provenance, source evidence and open items. Establish whether a separate existing reviewed release workflow already supplies this evidence before assigning production acceptance. Signature validity alone does not verify the source artifacts.

5. **Backup restore after ledger purge remains uncovered.** Confirmed the source/design finding in `handoffs/codex/round8-proposed-backup-history.md`: purge removes rows needed to identify older restored data, while restore accepts older timestamps and marks only surviving rows. Preserve that proposal; do not refuse recording an actual restore, invent a historical boundary, or call zero matches proof of safe restoration. Existing backup suite restores first and purges a separate old row afterwards, so it does not exercise the gap.
