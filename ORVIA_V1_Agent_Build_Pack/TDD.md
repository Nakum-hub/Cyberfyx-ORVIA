## 1. Design stance

**REQ:** customer-local privacy runtime; independent vendor commerce/support; one graph, policy, workflow, connector, evidence and testing model; one codebase across editions; no premature microservice expansion. **DESIGN:** retain TypeScript/React/Next.js, the current schema generator, PostgreSQL, OPA and Temporal, with a modular application and separately privileged workers/agents. The master permits an equivalent structured backend; no NestJS/ORM rewrite is required merely to satisfy a recommended-stack list. ## 2. Deployment units and trust boundaries

| Unit | Responsibility | Must not possess |
|---|---|---|
| Vendor public/account application | Product pages, checkout, designated contacts, licences/download eligibility and own cases | Runtime customer DB/connector credentials |
| Vendor staff application/API | Assigned organisation/case management, approved diagnostics, release metadata | Customer sessions, decryption/execution keys, remote support tunnels |
| Customer web/API host | Local Workspace/Privacy Centre adapters and authorised domain requests | Vendor release-signing private keys; unnecessary provider credentials |
| Customer policy service | Separate admin/processing namespaces, approved bundles/projections | Unrestricted target database access or a model dependency |
| Customer durable worker | Outbox delivery, typed orchestration, retries/reconciliation | Global vendor administration or cross-customer data authority |
| Customer connector agent/adapters | Bounded operations against authorised local/approved targets | Arbitrary shell/SQL, other connectors' secrets, unrestricted network |
| Customer persistence/observability | Domain data, workflow history, objects, local telemetry and backups | Vendor backup destination for operational data |
| Explicit evaluation/test composition | Synthetic targets, fixtures and fault injection | Automatic production activation or genuine client targets |

Logical modules do not imply one service each. A worker can host several workflow types with clear quotas and ownership. Vendor and customer builds may reuse source components, not live stores, cookie domains, signing keys or role authority. Public portal ingress is segregated from private admin APIs and databases; exact ingress/identity topology is a deployment decision with tests. ## 3. Dependency direction

```text
Browser feature -> generated customer client -> thin web/API adapter
                                             -> authenticated application service
                                             -> domain rules + unit-of-work/ports
                                             -> customer repository / connector port
                                             -> durable event + workflow/agent
                                             -> independent observation -> evidence

Vendor browser -> vendor API -> vendor store and approved payment/licence/release adapter
                               (no direct import of customer operational repositories)
```

Shared contracts contain serialisable schemas/types and generated clients, not database instances, secret resolution or privileged service objects. Mark backend-only entry points and check client bundles. The official Next.js guidance distinguishes server/client composition and the `server-only` import guard; that mechanism complements, not replaces, runtime authorisation. [Technical reference T1 in the decision register.]

For each implemented module, keep cohesive commands/queries and a small public API. Do not add a repository/service/controller/interface file for every function when one focused file is clearer. Split files by responsibility or security boundary, not an arbitrary line quota. A single giant dispatcher must not become the only place to add every future feature.

## 4. Scope and authentication model

**REQ:** validated trust domain plus organisation/legal entity/environment/optional subtenant and resource/action/context. **DESIGN:** request context is constructed only by verified session/service middleware. Scope parameters in a URL/body must be checked against authority; clients never select arbitrary context by sending `tenant_id`.

Keep current staff/principal session library and scoped-transaction safety; generalise configuration without removing validators. Add independent vendor-staff/commercial sessions with their own keys/stores/audiences. No global superadmin bypass. Resource queries, mutation plans, background jobs, search snippets, object downloads and notifications receive explicit authorised scope.

One primary owner is a local invariant. Bootstrap uses a single-use installation-bound claim, closes on success and records recovery readiness. Ownership transfer locks the organisation assignment, validates fresh approved authority, validates successor eligibility, changes the single assignment atomically and revokes obsolete authority as the approved policy requires. Invitation acceptance rechecks current delegator authority and expiry, not only a valid original token. Recovery is customer-held; no vendor password reset path. Sources: [§5](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-5), [§6](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-6), [§7](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-7), [§84](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-84), [§109](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-109).

## 5. Command pipeline

The common pipeline authenticates, rate-limits, authorises the capability/scope, validates canonical schema, verifies freshness/version and idempotency, runs an application service within its appropriate transaction, writes audit/outbox atomically where required, validates response and emits a safe result. Recheck material authorisation before a new irreversible effect after waiting/approval.

Use read models/projections for dashboards and bounded graph queries. Projection freshness is explicit. A stale projection must not authorise an irreversible action. Domain writes remain in the owning transaction; observers and long scans are not performed under broad unbounded DB locks. Compatibility behaviour is documented in [API contracts](API_AND_EVENT_CONTRACTS.md).

Do not conflate operation acceptance, workflow completion, target effect, verification and response delivery. Examples of state meanings and exact current enums are in the contract document. ## 6. Transaction and concurrency boundaries

| Boundary | Atomic invariant | External effects |
|---|---|---|
| Consent acceptance | Scope/principal/purpose lock; current expected epoch; one event/receipt/aggregate transition and outbox | None before commit |
| Policy publication | Exact version/digest, independent required review, immutable published version and event | Distribution follows committed publication |
| Owner transfer | One valid primary owner and audited successor change | Session/identity revocation executed through safe lifecycle |
| Action-plan approval | Approved digest/scope/generation/version/budget cannot drift | Execution revalidates before use |
| Import chunk | Validated immutable mapping/scope and idempotent row effect with provenance | No implied write to the original source |
| Diagnostic approval | Exact allowed payload digest/destination/purpose; local mapping stays local | Transfer only the approved immutable payload |
| Payment callback | Verified provider event deduplicated; commercial transition and entitlement task coherent | Licence generation has its own idempotent release/issuance boundary |

PostgreSQL is the domain transaction authority. Durable workflow history stores orchestration, not a competing consent truth. Outbox delivery is at-least-once; stable event/operation identity and digest-aware deduplication handle repetition. Keep global lock ordering and bounded lock waits; do not call a slow third-party service within a transaction intended to serialize all users. Preserve existing race-safety tests when optimizing. Sources: [§17](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-17), [§25](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-25), [§26](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-26), [§99](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-99), [§100](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-100), [§101](sources/ORVIA_V1_Unified_Master_Rev_1_4_Vendor_Support_and_Data_Onboarding.md#orvia-section-101).

**Decision requiring implementation review:** the current control path locks consent while querying its synthetic target. A production adapter must define how fresh policy/consent checks relate to the actual send/effect boundary; simply moving the read outside the transaction can reopen a race. Design a short final admission or scope/epoch-bound use check and prove it with concurrent revoke/send tests. Do not promise atomicity across unrelated target databases.

## 7. Graph, discovery and source authority

Use normal relational records and explicit relationship tables for high-value entities; JSONB is for versioned documents/connector-specific validated attributes, not every relationship. Identity, purpose, source/interpretation, data-copy and processor relationships need provenance and current/historical reference semantics.

Discovery runs in a bounded job using granted read permissions. Store declared, discovered and observed relationships distinctly. Review a changed schema/destination before approving purpose or control scope. Partial pages or revoked credentials create incomplete/stale coverage; no universal inventory-complete flag. Prepare immutable snapshots for impact analysis and keep the original graph context resolvable from evidence. ## 8. Policies and runtime control

Retain OPA as the selected implementation baseline unless an approved ADR justifies a change. Define separate admin and processing inputs/tests. Author policy using versioned reviewed rules, not raw user-supplied executable code. Compile approved projections asynchronously and pin source/interpretation/applicability versions.

The `privacy-control` module owns admission/enforcement orchestration at supported boundaries, not the entire product. It consumes consent/current-authority reads, policy decisions and connector/observation ports. It records decision version, epoch, scope, purpose and obligations. SDK consumers must implement mandatory MASK/RESTRICT obligations or reject/escalate. A previous ALLOW or preview is not indefinite permission.

Remove residual knowledge of synthetic table names and connector enum branches as production adapters are introduced. Keep a tested synthetic composition for regressions. Full graph traversal, large reports and model calls remain outside the hot path. Signed bundle freshness, rollback and missing-service behaviour are explicit; vendor outage and local policy outage are different events. ## 9. Durable execution, plans and agents

Define one execution plan with stable operation identity and version, precise target set/generation, consent/policy/applicability references, approval, budget and verification plan. Dispatch only supported typed commands. Customer command keys differ from vendor licence/release keys.

The agent independently checks the whole binding and local permission state. Poll/transport errors do not become action success. Record an attempt before delivery, a receipt separately, and then independently observe. Unknown effects enter reconciliation; no blind repeated deletion when neither idempotence nor observation is available. Bound retries with backoff, jitter, attempt limits, circuit breaker and a visible review/dead-letter path. Exact retry values are connector configuration, not universal defaults.

Temporal definitions need a versioning/replay strategy; retain workers compatible with existing histories or use tested patching for the selected server/SDK. Official Temporal documentation requires deterministic workflow definitions and describes versioning approaches; do not copy obsolete APIs without checking installed versions. [T3.] Domain permission/expiry checks still run at activity/effect time. ## 10. Rights, retention, processor and incident composition

Rights intake creates a request with independently tracked identity/mandate, scoping, execution and response. Each request type uses the shared plan/workflow/evidence engine, not a new bespoke job system. Access responses require authorised redaction and expiring local delivery. Nominee/guardian revocation blocks new privilege; authority to request is not account takeover.

Retention evaluates data copies and purposes, not one global person-level deadline. Conflicts create restricted-retention/hold decisions with a review owner. Deletion plans separately represent suppression, live copies, derived stores, processors and backup expiry/restore controls. Unsupported erasure remains a gap.

Processor assessments, findings and SDF workflows connect to graph/control references. Incident clocks retain original trigger records and corrections; recipient/regime tasks have separate approval/dispatch evidence. No hard-coded universal deadline or automatic regulator submission. ## 11. Vendor commercial and support architecture

Use a separate vendor deployment/store. Commercial accounts hold designated contacts, not customer runtime users. Invoice/payment truth comes from the approved provider's verified server interaction, not UI redirects. Entitlement issuance is idempotent, versioned and auditable. Provider and commercial term selection remain OPEN.

Local licences verify against vendor public trust material but never authorise customer operations directly. Expiry/downgrade invokes an approved local continuity table. Do not use runtime client counts/events for vendor billing where §31 forbids them.

Support intake accepts one exact customer-previewed approved schema. A proposed local egress broker checks purpose/destination/payload/digest and transmits only that stored payload. Retry of the same approved delivery can reuse its delivery identity within the explicit approval scope; creating a new payload requires new approval. No scheduled diagnostics, inbound command agent, raw logs or remote support API. Vendor case closure updates vendor facts only. ## 12. Local imports and file handling

Quarantine locally, identify supported type/schema, validate limits and content, map explicitly, preview a frozen scope and record approval. Stage source date/digest and mapping version. Validate duplicates, identifier ambiguity and conflicts before row effects. Choose and document all-or-nothing versus chunked partial import; a partial import reports exact committed/rejected counts within authorised local views.

Importing legacy consent never overrides newer live withdrawal automatically. A file snapshot creates no source-system connection. Originals, staging, per-row errors and previews have explicit local retention; error reports may contain personal data and require the same controls. No public scanning service or vendor file copy. ## 13. Frontend and reporting implementation

Keep framework routes thin and feature code cohesive. Shared UI primitives may be reused across separate builds, but vendor bundles must not embed customer operational configuration/data. Use canonical generated clients and state descriptions. The route/API separation does not require another framework merely for directory aesthetics.

Every sensitive page revalidates authorisation server-side, even when navigation hides actions. Poll async operations using bounded intervals and cancellation; current server response and `as_of`/freshness determine presentation. Do not guess progress percentages. Browser closure does not cancel accepted work.

Graphs need an accessible table/list alternative. Tables use server-side scoped pagination and explicit totals/coverage denominator. Exports run as bounded jobs where necessary; CSV/PDF rendering must not fetch arbitrary external resources or execute customer formula/markup. ## 14. Persistence, deployment and recovery

Use [DATA_MODEL](DATA_MODEL.md) for vendor/customer separation, constraints, retention and migrations. Secrets resolve locally. Domain DBs, workflow persistence, file/object storage and observability may be separate services/stores; physical topology is an explicit supported-profile decision. Redis is optional for a real need, never consent authority.

Build the complete licensed runtime as signed versioned artifacts in the canonical ZIP envelope. Keep evaluation and production manifests/configuration distinct; synthetic fixtures cannot be default production bootstrap. Production Temporal persistence, policies, database roles, TLS, keys, local UI assets, backup and safe import/update must work without vendor connectivity or model services.

The master requires reconciliation, not magically available state.

## 15. Performance and resilience qualification

Measure source candidate targets, not speculative guarantees. Define hardware/profile, dataset sizes, representative mix, hot/cold cache, concurrency, target latency and workload bounds. Separate control admission from exports/scans/tests through quotas. Bound DB pools and transaction locks by measured capacity rather than retaining a prototype value as a production standard. Fault injection includes network partitions, policy outage, storage/full spool, secret-store failure, lost receipts, cancellation and interrupted upgrade.

No production release with known blocking isolation/privacy/execution defects or unresolved applicable Critical/High findings. Independent security and customer-environment qualification are not replaced by two coding agents reviewing each other.
